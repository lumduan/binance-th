# ADR-0003 — Request signing and parameter ordering (HMAC-SHA256)

- **Status:** Accepted
- **Date:** 2026-07-09
- **Governs:** FR-AUTH-01 · WBS-M1-05

## Context

SIGNED endpoints (orders, account, wallet) authenticate with an `HMAC-SHA256` signature over the
request parameters, keyed by the API secret. The Phase-1 order models already encode the intent that
`timestamp` and `signature` are **auto-generated by the client**, not supplied by the caller
(`binance_th/models/orders.py:6-24`), and the secret is held as a `SecretStr`
(`binance_th/config.py:65`).

The Binance signing scheme has three well-known footguns that must be decided once, because getting
any of them wrong produces an opaque `-1022 Signature for this request is not valid`:

1. Parameters are signed in the **order they are sent**; the server re-derives the string from the
   received query, so the signed string and the sent string must be byte-identical.
2. For requests that carry both a query string and a form body, the signature covers the **raw
   concatenation** `query_string + request_body`.
3. Signing is over **raw** parameter values; the `signature` field is appended **last** and is
   itself **never** part of the signed string.

⚠ ASSUMED (verify at implementation): the exact concatenation rule and whether TH uses total-params
signing identically to Binance global — locked by a golden vector captured against the live API.

## Decision

**We will construct signed requests from an insertion-ordered parameter mapping** and compute
`signature = HMAC_SHA256(secret, raw_concat(query, body))` over the **raw** (un-URL-encoded) values,
append `signature` as the final parameter, and never include it in the signed material. `timestamp`
(and optional `recvWindow`) are injected by the signer immediately before hashing
([ADR-0004](./ADR-0004-server-time-offset-and-1021-resync.md)). A **golden-vector unit test** pins
known params + a known secret to a known signature so any regression in ordering or encoding fails
loudly and offline.

Falsifiable: reordering two params changes the signature; the `signature` param does not appear in
the signed string; the golden vector reproduces the expected digest bit-for-bit.

## Consequences

**Positive**

- Deterministic, offline-testable signing decoupled from network flakiness.
- Insertion-ordered construction makes the "sign what you send" contract structural, not incidental.

**Negative / trade-offs accepted**

- Parameter order is load-bearing: any code path that rebuilds the param map through an unordered
  structure can silently break auth. Mitigated by building on `dict` (insertion-ordered in 3.12) and
  the golden-vector guard.

## Alternatives Considered

- **Sort parameters alphabetically before signing** — rejected: the server signs the received order,
  not a canonical sort; sorting would mismatch.
- **URL-encode values before hashing** — rejected: the server hashes raw values; encoding first
  yields a different digest.
- **Sign query and body independently** — rejected: the scheme concatenates them into one signed
  string.
